# contracts: o que o frontend e o backend trocam

`game.schema.json` é o **contrato** entre o TypeScript e o Python, em JSON Schema. Ele é **gerado**, nunca editado na mão: a fonte única são os tipos do TS.

## Por que na raiz

O contrato não é do frontend nem do backend, é dos dois. Na raiz, `frontend/` escreve e `backend/` lê, sem um apontar para dentro do outro.

## O que tem dentro

| Definição | De onde vem | Para quê |
|---|---|---|
| `GameCommand` | `game/domain/core/commands.ts` | Cada jogada que o cliente manda (`rollDice`, `playCard`…), separada pelo campo `type` |
| `CommandResult` | `game/application/gameClient.ts` | Resposta do `send`: `{ ok: true }` ou `{ ok: false, code }` |
| `GameErrorCode` | `game/domain/core/errors.ts` | Os códigos de recusa (`NOT_YOUR_TURN`…) |
| `SnapshotMessage` | `Snapshot` do `gameClient.ts` | Estado completo ao entrar/reentrar na sala |
| `GameUpdateMessage` | `GameUpdate` do `gameClient.ts` | Cada jogada aceita, com `seq` |

`state` (`GameState`) e `events` (`GameEvent[]`) saem como `OpaqueJson` (um objeto qualquer): o FastAPI só guarda e repassa, quem entende as regras é o serviço Node (opção B do [backend-plano.md](../docs/backend-plano.md)). Assim o schema não muda a cada regra nova.

A lista de tipos exportados fica em `frontend/src/game/application/contract.ts`; os nomes que viram raiz do schema, em `frontend/scripts/contract/generate-schema.mjs` (`ROOT_TYPES`).

## O fluxo

1. Muda um tipo no TS (ex.: um campo novo num `GameCommand`).
2. Em `frontend/`: `npm run schema` (usa o [ts-json-schema-generator](https://github.com/vega/ts-json-schema-generator)).
3. Commita o `game.schema.json` junto com a mudança do TS.
4. No backend, regenera os modelos Pydantic (comando abaixo) e ajusta o código que usa.

O CI roda `npm run schema` e falha (`git diff --exit-code`) se o arquivo commitado estiver diferente. Para conferir na sua máquina sem escrever nada: `npm run schema:check`.

## Gerando os modelos Pydantic

Com o [datamodel-code-generator](https://github.com/koxudaxi/datamodel-code-generator), de dentro de `backend/`:

```bash
uv add --dev datamodel-code-generator
uv run datamodel-codegen \
  --input ../contracts/game.schema.json \
  --input-file-type jsonschema \
  --preset standard-py312-20261106 \
  --use-tag-as-union-variant-name \
  --output app/contracts/game.py
```

- `app/contracts/game.py` é **gerado** (o cabeçalho diz `generated by datamodel-codegen`): não edite, regenere. Os `schemas.py` de cada módulo (`app/modules/...`) importam dele, igual ao `contracts/` da raiz servindo os dois lados.
- `--use-tag-as-union-variant-name` dá nomes legíveis às variantes: `GameCommandRollDice`, `GameCommandPlayCard`… (sem ele viram `GameCommand1`, `GameCommand2`…).
- O preset gera os campos em snake_case com alias para o camelCase do JSON (`player_id` ↔ `playerId`). Ao devolver JSON, use `model_dump(by_alias=True)` (ou `response_model_by_alias`, o padrão do FastAPI).
- `GameCommand` é um `RootModel` com a união: `GameCommand.model_validate(dados).root` devolve a variante certa, e um `type` desconhecido vira `ValidationError`.
- Testado com datamodel-codegen 0.93.0 (11/11/2026). Se mudar a versão do Python do backend, troque `py312` no preset.
